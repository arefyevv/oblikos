# Блог Oblik OS: отчёт о реализации

Дата: 6 октября 2026 года.

## Результат

Добавлены `/blog` и `/blog/[slug]`: адаптивная сетка, шесть категорий, работающий
фильтр, пять демонстрационных статей, автор, даты, обложки, теги, оглавление,
связанные материалы и CTA «Создать своего AI-персонажа» на
`https://app.oblikos.ru/register`. Неизвестный slug возвращает HTTP 404.

Используются существующие Manrope, зелёная палитра, логотип, Badge и ButtonLink.
Обложки взяты из утверждённых изображений лендинга. Глобальные стили, маршруты
и основная навигация кабинета не изменены. Новых npm-зависимостей, CMS и mock API нет.

## Архитектура двух приложений

Фактическая структура отличается от одного общего Next.js-приложения:

- `Site/`: публичный лендинг на React + Vite, основной домен `oblikos.ru`.
- `App/`: Next.js App Router, кабинет на `app.oblikos.ru`.

Блог реализован в `App/`, вне `(workspace)` и `(auth)`, без проверки сессии.
Его канонический адрес — `https://oblikos.ru/blog`. Для основного домена
подготовлен `deploy/blog-public-locations.conf`: он направляет только блог,
его статические ресурсы, sitemap и robots в существующий Next.js-сервер.
Корень сайта продолжает обслуживать Vite-лендинг. Конфигурация поддомена
предусматривает 301 с `/blog` и `/blog/*` на основной домен.

В `Site/vite.config.ts` аналогичная схема работает локально через proxy.
По умолчанию Next.js ожидается на `http://127.0.0.1:3000`; для другого порта
используйте `BLOG_DEV_TARGET`. Проксируются также RSC-запросы с query string.

**Обновление после публикации, 6 октября 2026 года:** пользователь выполнил
deploy приложения; на хостинге также обнаружен обновлённый лендинг. После диагностики применена
маршрутизация Nginx на реальном VPS: фактический порт службы — **3001**.
Блог работает на основном домене, поддомен перенаправляет его через 301.
Один только Vite build не публикует Next.js-маршруты.

## Где находятся статьи и как работает получение данных

Каждая статья — отдельный типизированный объект `BlogPost` в
`src/features/blog/posts/`. Текст хранится в поле `content`.
Модель содержит все поля из ТЗ; category — стабильный slug из реестра категорий.
Русские названия категорий отделены от slug, что позволяет позже добавить
`/blog/category/[slug]` без изменения статей.

`repository.ts` предоставляет асинхронные `listBlogPosts`, `getBlogPost` и
`relatedBlogPosts`. Страницы, метаданные и sitemap используют этот единый источник.
При загрузке проверяются slug, даты, категория, обязательные поля и обложки;
дубли slug и дата обновления раньше публикации приводят к ошибке.
Список отсортирован по публикации. Related articles ранжируются по совпадению
категории и тегов, затем по дате; сама статья исключается, выводятся до трёх.

Блог и демонстрационные статьи предварительно генерируются при сборке.
Клиентскому фильтру передаются только краткие данные карточек, без тел всех статей.
При подключении CMS источник заменяется внутри repository; отдельно потребуется
настроить кеширование, обновление и публикацию новых данных.

## Как добавить статью

1. Создайте файл в `src/features/blog/posts/` и экспортируйте объект типа `BlogPost`.
2. Заполните уникальный slug строчными латинскими буквами с дефисами, title,
   description, publishedAt, author, category, tags и content. Даты указывайте
   в ISO 8601 с часовым поясом. excerpt, updatedAt и coverImage необязательны.
3. Выберите category из `blogCategories` в `types.ts`:
   `ai-characters`, `ai-influencers`, `content`, `marketing`, `guides`, `cases`.
4. Добавьте обложку в `public/blog/media/` и путь `/blog/media/имя.webp`.
   Если обложки нет, используется существующий портрет Софии.
5. Импортируйте объект и добавьте его в массив `posts` в `repository.ts`.
6. Запустите typecheck, lint и build. После следующей сборки появятся страница,
   карточка, метаданные и запись sitemap; отдельные правки маршрутов не нужны.

Поддерживается небольшой безопасный поднабор Markdown: абзацы, заголовки `##`
и `###`, списки с `- ` или `1. `. Разделяйте блоки пустой строкой.
Оглавление строится тем же парсером, что и контент; якоря уникальны даже при
повторяющихся заголовках. HTML не исполняется. Встроенные ссылки, изображения,
таблицы, выделение и MDX-компоненты сейчас не разбираются. При необходимости
полного Markdown замените этот модуль зрелым парсером с тем же выходным интерфейсом.

Демо-статьи содержат 601, 630, 630, 630 и 644 слова соответственно. Это
демонстрационные редакционные материалы, не исследования и не реальные кейсы.

## SEO

- Next.js Metadata API: title, description, абсолютный canonical,
  Open Graph, Twitter summary_large_image, автор и теги.
- Тип Open Graph `article`, publishedTime и modifiedTime для статей.
- JSON-LD `BlogPosting` и `BreadcrumbList`, включая абсолютные URL,
  автора-редакцию, издателя, обложку, даты, категорию и язык.
- Безопасная сериализация JSON-LD с экранированием `<`.
- Один h1 статьи, h2/h3 в тексте, видимые хлебные крошки и оглавление.
- Блог переопределяет root noindex на `index, follow`; настройки кабинета
  остаются прежними.
- Sitemap содержит главную публичную страницу, `/blog` и все пять статей.
  Служебные auth-страницы и кабинет исключены. lastModified берётся из даты
  обновления или публикации, а не из произвольного времени сборки.
- Robots разрешает корень, блог и нужную статику, закрывает остальные пути
  приложения и указывает sitemap основного домена.

В существующей `.figma/make/site.json` лендинга уже установлен `robots.index=false`.
Этот отдельный запрет индексации главной страницы не изменён в рамках блога.
Новые blog-страницы получают HTML из Next.js и не наследуют Vite noindex.
На production `/robots.txt` должен обслуживаться новым Nginx location:
старый `Site/dist/robots.txt` запрещает обход всего сайта.

- Итоговый `npx playwright test --config playwright.blog.config.ts`: **4 passed**.

- Адаптивность на 320, 390, 768 и 1440 px: горизонтального переполнения нет,
  сделаны скриншоты. Desktop и mobile скриншоты просмотрены визуально.
- Связка Vite → Next.js: переход из desktop/mobile меню лендинга,
  прямая перезагрузка статьи, ресурсы, sitemap, robots и RSC через proxy.

Команды из `App/`:

```powershell
npm run typecheck
npm run lint
npm run build
$env:BLOG_LANDING_ORIGIN = 'http://127.0.0.1:5175'
npx playwright test --config playwright.blog.config.ts
```

Тестовая конфигурация самостоятельно запускает Next.js на 3001 и Vite на 5175,
использует отдельный `.next-e2e` и завершает тестовые серверы после проверки.
После сообщения об отсутствии блога выполнена отдельная production-проверка:
`/blog` и все пять статей возвращают 200 с нужным содержимым; 19 ресурсов
блога доступны с корректными MIME; schema и canonical присутствуют; sitemap
содержит все статьи; robots разрешает блог; `app.oblikos.ru/blog` возвращает
301 на основной домен. Обновлённая ссылка присутствует в опубликованном JS лендинга.
Результаты поисковой индексации не проверялись.

Конфигурация подключена через `/etc/nginx/snippets/oblikos-blog.conf`;
проверка `nginx -t` и reload прошли. Резервные копии двух исходных vhost-файлов
находятся в `/etc/nginx/blog-backups/20261006-204525-309376`.
Скрипт `scripts/enable-blog-routing.py` повторяет эту настройку с определением
порта из systemd, проверкой блога, резервными копиями и восстановлением при ошибке.
